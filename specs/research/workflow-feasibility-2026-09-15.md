The first planning decisions are the editor roster, whether unpublished material must be confidential even from people reading GitHub or obtaining media URLs, and whether changing the repository default to `development` is acceptable. The companion repository audit also reports no existing `development` branch, so the plan must reconcile that mismatch with the staged intent before treating the shared branch as ready.

Recommended implementation order: resolve those decisions; prepare one representative Tina-editable page and shared content; prove Access, media persistence, generated bindings, repeat deployment, and Free CPU limits on a protected trial deployment; then expand the content model and release workflow. The trial is proposed implementation work, not work performed by this note.

No actual Tina project, Cloudflare plan/policy, authentication session, editing endpoint, or deployed CPU measurement was inspected during this research. Repository-specific public/default-branch findings above come from the companion audit, not from these external sources. Exact dependency compatibility and live-account feasibility remain acceptance evidence to collect.

## Follow-up: one Tina login used by several people

Later on 15 September, the originator selected workflow implementation first, keeping GitHub public with draft-source visibility accepted, and uploading only media approved for public exposure. They requested one Tina account used by multiple people. That new request replaces the staged specification's no-sharing assumption for planning; the provider's seat definition and observed login behaviour still need to be distinguished.

| --- | --- |

Section 1.4 prohibits identity misrepresentation and bypassing service-use restrictions. No reviewed clause expressly prohibits all owner-authorised sharing or defines its seat treatment. The published terms are dated 10 May 2024. [Tina terms](https://tina.io/terms-of-service) |

## Follow-up: gracefully handling overlapping editing attempts

The originator clarified that **four people** will share the Tina identity, normally one at a time. Simultaneous editing is unnecessary; a second attempt should be prevented or handled clearly. This research inspected Tina's current source at commit `f27d2e5c566c38ae236c80d680ea36530fdf470d`. It does not establish that this commit is a published package or that the eventual pinned version behaves identically.

- **A cancellable normal-save hook exists.** Collection `ui.beforeSubmit({ values, cms, form })` runs in the browser. `FormBuilder` attaches it to the form; `Form.handleSubmit` awaits it before calling `onSubmit`, catching thrown errors into `FORM_ERROR`. Therefore an asynchronous check can reject an ordinary form save. Returning `undefined` does not cancel it. No collection-level after-submit hook was established; `Form.onSubmit` exists in source, but replacing/wrapping it needs integration testing. [Hook documentation](https://tina.io/docs/extending-tina/before-submit), [FormBuilder source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/toolkit/form-builder/form-builder.tsx#L110), [Form submission source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/toolkit/forms/form.ts#L228).
- **No native stale-revision protection was verified.** The normal update mutation sends collection, relative path, and values, without an expected revision/hash. The inspected open-source resolver likewise accepts content and paths without a compare-and-swap argument. This does not prove what additional checks TinaCloud's private backend performs, but it provides no basis for promising that a stale editor's save will be rejected. [Admin mutation source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/admin/api.ts#L24), [Resolver source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/%40tinacms/graphql/src/resolver/index.ts#L863).
- **Entry protection is insufficient.** The authenticated browser posts mutations directly to TinaCloud's content endpoint. Protecting `/admin` or Astro's refresh route cannot stop saves from an already-open editor. A pre-submit lease check also leaves a race between that check and the subsequent upstream mutation. Current session-expiry handling sends a 401 response back to login; that is not lease expiry or stale-content detection. [Browser client source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/internalClient/index.ts#L218).
- **Media requires separate coverage.** Collection hooks do not wrap all media mutations or document deletion. Media has `persist`, `delete`, optional `rename`, and related operations; its emitted start/success/failure events are notifications, not a documented asynchronous veto. Collection `allowedActions` covers creation/deletion/folder controls, not a dynamic per-session edit lock. [Media source](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/toolkit/core/media.ts#L66), [Collection UI types](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/%40tinacms/schema-tools/src/types/index.ts#L1281).
- **A write proxy is an integration change.** `contentApiUrlOverride` is documented, and a custom media store is supported. However, current default repo-media rejects nonlocal custom content APIs as unsupported self-hosting. Simply pointing content at the Worker can therefore break media. `tinaioConfig` content/assets overrides exist but are marked primarily internal. A gateway must validate hosted authentication and both content/media paths; it is not an established one-setting solution. [Configuration documentation](https://tina.io/docs/reference/config), [Default media guard](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/tinacms/src/toolkit/core/media-store.default.ts#L174), [Internal override types](https://github.com/tinacms/tinacms/blob/f27d2e5c566c38ae236c80d680ea36530fdf470d/packages/%40tinacms/schema-tools/src/types/index.ts#L1128).
- **A Free atomic coordinator is available.** SQLite-backed Durable Objects are available on Workers Free; their storage supports atomic transactions. Workers KV is eventually consistent and explicitly unsuitable for atomic acquisition. An HTTP heartbeat avoids the previously noted Worker-level Access WebSocket restriction. This supports a possible lease coordinator, not a complete Tina locking claim. [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [Transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactions), [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/#consistency).

**Recommendation:** start with a short integration spike for a website-wide editing reservation, a waiting screen for the second editor, and uninterrupted read-only review. Identify the holder through individual Access identity plus a browser-session token rather than the shared Tina identity. Use an atomic holder/session record, HTTP renewal, explicit release, a clear lease-loss message, and owner recovery. A new holder must reload saved content; an old session must never silently resume stale editing. The inspected form handler skips reinitialisation when `beforeSubmit` rejects; verify that the final GUI shows the error and preserves unsaved work. Test save/create/delete/upload/rename operations, two browsers, suspended tabs, network loss, and browser crashes.

An admission screen plus heartbeat and `beforeSubmit` checks is a **cooperative accident guard**, not a guarantee against every stale or in-flight write. Stronger prevention requires ownership checking at the actual normal-GUI mutation gateway and preventing handover while an upstream mutation remains in flight. A timeout or disconnected browser does not prove the upstream write failed; ambiguous operations need reconciliation before recovery. Direct TinaCloud clients and developer Git pushes would still require team coordination. No hostile-client protection is proposed.

The plan should make that spike an acceptance gate. If complete mutation coverage requires substantial custom integration, present the concrete choice between accepting the documented cooperative limitation and building the stronger gateway. Do not describe an expiring front-end lease as a verified Tina lock, and do not quietly remove graphical media editing to simplify it. No locking implementation, deployment, installation, or account change was performed.
